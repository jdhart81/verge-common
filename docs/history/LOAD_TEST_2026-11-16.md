# Load and failure test — 16 November 2026

A local test of the self-hosted server on the code in PR #101, before land-trust projects start. One process, one SQLite file, woodland on, heap limited to 512 MB (production's container reports a 560 MB heap limit and 2 CPUs). Test machine: 2 cores at 2.1 GHz. Synthetic accounts and data only; nothing touched production.

The co-op under test: 30 members, two stewards, one woodland project with 265 KB of reviewed corridor layers. One member's view of it is 303 KB.

## Results

| What | Result |
| --- | --- |
| Sign-up, one after another | 230 ms each |
| One member alone: save a post | 75 ms |
| One member alone: load the whole co-op | 37 ms |
| One member alone: refresh, nothing changed | 7 ms |
| 30 members refreshing together, nothing changed (600 requests) | 171 a second, no errors |
| 30 members loading the whole co-op together (600 requests) | 37 a second, no errors; each waits about 4 s at that pace |
| 30 members posting at the same instant | all 30 saved in 3.0 s, no conflict shown to anyone, none lost, none duplicated |
| 6 corridor analyses asked for at once by two members | each member's first ran (10 s for the slowest); the rest were told one is already running |
| Peak server memory during all of the above | 519 MB |
| Server killed (`kill -9`) in the middle of 25 simultaneous posts, twice | restarted healthy; every acknowledged post was stored; none duplicated; audit sequence contiguous; hash chain intact; `PRAGMA integrity_check` ok; backup and restore check passed |

## What the test changed

Three things were found and fixed in the same pull request.

1. **Saving from a page that was behind failed.** Any save was refused if anyone else had saved since the page last refreshed (up to 30 seconds earlier), and the member had to press the button again. Now a command that only adds the sender's own new record (an update, a comment, an RSVP, a report, a parcel, a vote) is applied to the co-op as it stands. Everything that reviews, approves or changes an existing record still needs the version the sender saw.
2. **Simultaneous saves redid each other's work.** 30 members posting at once took 17 s, because each request read, applied and hashed the whole co-op and all but one lost the race and started again. Saves to one co-op now run one after another inside the server: 3.0 s for the same 30, with no retries.
3. **Counting storage cost a third of every save.** The co-op was serialized several times per save to measure it. It is now measured in one pass: a save on this co-op went from 146 ms to 75 ms.

## Limits that remain

- **One steward, 40 commands a minute.** Approving 30 new members in one sitting (an invitation and an approval each) hit the per-account limit. Spread across two stewards, or over two minutes, it does not.
- **A co-op is still one record.** Every save rewrites it and every changed refresh downloads it. At 300 KB this is 75 ms and 37 ms. It is the reason corridor records are capped at 2.5 MB per co-op.
- **One analysis per member at a time**, and the slowest takes about 10 s at the largest layer size on this machine. The production server's speed was not measured.
- **One server.** No failover; a restart takes about ten seconds, during which requests fail and the app retries its refresh.
- Not measured: many co-ops at once (each is independent, so this should scale with CPU), evidence uploads under load, and real network latency.
