# VergeCommon launch kit

## Positioning

**What if conservation could be an open-source project? Enter VergeCommon.**

Open tools for people caring for the places they share. Organize conservation projects, document field work, and make decisions together.

Launch this as an **early contributor preview**. The immediate ask is to try a local workflow and contribute one useful improvement. The initial success milestone is one independent community completing a useful activity and returning for a second one. Stars, impressions, downloads, and test results do not establish adoption or ecological impact.

## Announcement draft — not posted

What if conservation could be an open-source project?

Enter VergeCommon: open tools for people caring for the places they share.

We’re building a shared workspace for conservation projects: community activities, private field records, project mapping, and cooperative decisions. Communities can inspect the code, adapt the workflows, and contribute improvements back.

This is an early contributor preview. We’re inviting conservation practitioners, community organizers, designers, researchers, and developers to help shape it. You don’t need to write code: try a workflow, tell us what is missing, or improve a guide.

The code is AGPL-3.0-only. Private land and participant records are not public data. The software does not certify environmental outcomes, issue carbon credits, or send payments.

Start with the source and local setup instructions:
https://github.com/jdhart81/verge-common

Our first milestone is simple: help one community do useful conservation work, then come back and do it again.

## Hosted pilot gates

These remain open until evidence is recorded. The source contributor preview does not satisfy them.

- Explicitly approve the hosted audience and verify sign-in using two independent accounts.
- Independently review authentication, membership, private files, and authorization.
- Rehearse database and file restore; document the operator and recovery result.
- Establish moderation, incident response, retention/deletion handling, and production abuse controls.
- Complete [pilot acceptance](PILOT.md), including mobile and accessibility checks with real participants.
- Confirm local consent and the suitability of any legal or ecological workflow with qualified reviewers.

Do not present native authenticated participation, App Store distribution, ecological certification, registry execution, or payment execution as available. See [architecture](ARCHITECTURE.md), [security](../SECURITY.md), and [roadmap](../ROADMAP.md).

## Launch-day sequence

1. Review the release candidate, validation receipt, and unresolved gates.
2. Publish the approved source revision; verify its CI and contributor links.
3. Publish the approved contributor announcement linking to that repository.
4. Triage newcomer reports into bounded tasks and acknowledge actual contributions.
5. Record whether an independent person completed local setup and a useful workflow. Pursue a consenting hosted pilot only after its separate gates are met.
